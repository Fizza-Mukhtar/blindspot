# Prior art

Blindspot is not the first system to generate tests from a specification, and it is not
the first to notice that a model's own tests are weak evidence about its own code. This
document says exactly what already exists, exactly where Blindspot sits relative to it,
and which of this project's claims are supported by published work versus measured here.

**Every reference below was fetched from the arXiv API and its title verified** before
being written down. Nothing here is cited from memory — and that claim is a command rather
than an assurance:

```bash
make verify-citations     # re-queries arXiv for every id in every Markdown file
```

It reports the real title of each paper and fails on any id that arXiv does not know. It is
the only check in this repository that needs the network, which is why it is deliberately
not part of `make check`.

## 1. The closest work

### Ma & Eisty — *From Business Requirements to Test Assertions: Evaluating LLM-Generated Oracles on Real Bugs*
<https://arxiv.org/abs/2607.10277>

The nearest neighbour. Generates test oracles from natural-language requirements **without
access to source code**, on 10 real Defects4J Lang bugs whose requirements were manually
translated by the authors, scoring five models' oracles against a hand-built gold standard.

*How Blindspot differs.* Theirs is an offline measurement of oracle quality; Blindspot is
an end-to-end audit that has to decide what to tell a human. That difference forces three
things their setup does not need: a soundness criterion checked by execution rather than
by comparison to a gold oracle, a triage step for failing tests that are the *test's*
fault, and an escalation path for requirements that genuinely do not determine an answer.
Their headline finding — that requirement-derived oracles align with the requirement more
than with the system under test — is the effect Blindspot's ambiguity gate and referee
exist to manage rather than to suffer.

### PGS — *Effective LLM Code Refinement via Property-Oriented and Structurally Minimal Feedback*
<https://arxiv.org/abs/2506.18315>

Introduces the Property-Generated Solver: derive high-level properties (a sort must
produce a non-decreasing sequence), check them, and feed back the simplest failing
counterexample.

*How Blindspot differs.* PGS uses spec-derived properties as **repair fuel** — the
counterexample is an input to a better generation loop, and success is measured as
improved pass@k. Blindspot uses them as an **audit** — the counterexample is the
deliverable, handed to a human as a runnable regression test, and success is measured as
detection at a controlled false-alarm rate. The two are complementary: PGS makes the code
better, Blindspot tells you whether to believe it.

### Nexus — *Execution-Grounded Multi-Agent Test Oracle Synthesis*
<https://arxiv.org/abs/2510.26423>

Four specialist agents deliberate over candidate oracles, then validate them by generating
a *plausible candidate implementation* and executing the oracles against it in a sandbox.

*How Blindspot differs.* Nexus validates against a **synthesised** implementation, so a
shared misreading between the oracle-writer and the implementation-synthesiser survives
validation — the same correlation problem one level up. Blindspot validates against a
**hand-written reference that the system never sees**, which is why its soundness check
cannot be satisfied by agreeing with a model. Nexus also separates agents by *testing
philosophy*; Blindspot separates them by *what they are allowed to read*, and measures the
difference (see the roles-vs-information ablation in [CHANGELOG.md](CHANGELOG.md)).

### SpecPylot — *Python Specification Generation using Large Language Models*
<https://arxiv.org/abs/2604.16560>

Generates formal specifications/contracts for Python code. Runs in the opposite direction:
it reads the implementation to produce a specification, which is precisely the dependency
Blindspot is built to avoid.

## 2. Evidence the project's thesis rests on

| Claim | Source |
|---|---|
| Passing tests are weak evidence of correctness: pass@k drops substantially under stronger test suites | *Is Your Code Generated by ChatGPT Really Correct?* (EvalPlus) — <https://arxiv.org/abs/2305.01210> |
| LLM-generated oracles tend to capture the code's **actual** behaviour rather than its **expected** behaviour | Konstantinou et al. — <https://arxiv.org/abs/2410.21136> |
| Conditioning test generation on the code under test measurably changes what the tests find | *Measuring the Influence of Incorrect Code on Test Generation* — <https://arxiv.org/abs/2409.09464> |
| Verification and generation are different competencies; LLM errors cluster rather than scatter | *Rethinking Verification for LLM Code Generation* — <https://arxiv.org/abs/2507.06920> |
| Coverage and mutation score stop tracking effectiveness for LLM-written suites | <https://arxiv.org/abs/2607.22880> |
| Oracle-generation results look far better under leakage than under realistic evaluation | *Towards More Realistic Evaluation for Neural Test Oracle Generation* — <https://arxiv.org/abs/2305.17047> |
| Producing a failing test from a specification is a distinct, hard task with a low ceiling | *SWT-Bench* — <https://arxiv.org/abs/2406.12952> |
| Specifications are routinely ambiguous and models guess silently instead of asking | *HumanEvalComm* — <https://arxiv.org/abs/2406.00215> |
| Tests as a formalisation of intent improve outcomes when a human is in the loop | *LLM-Based Test-Driven Interactive Code Generation* — <https://arxiv.org/abs/2404.10100> |
| Models do not reliably self-correct without external signal (influential, and contested) | <https://arxiv.org/abs/2310.01798> |
| **Counter-evidence, cited deliberately:** LLMs asked to check code against natural-language specs over-flag correct code | *Uncovering Systematic Failures of LLMs in Verifying Code Against Natural Language Specifications* — <https://arxiv.org/abs/2508.12358> |

That last row is why Blindspot reports a **false-alarm rate on clean implementations** as a
first-class metric rather than a footnote, and why the referee's calibration is
deliberately biased towards `bad_test`. A spec-blind falsifier's characteristic failure is
a confident, wrong accusation; a system that does not measure that is not reporting its
real performance.

### On benchmark validity

*The Benchmark Ceiling: Human Judgment, Evaluation Scarcity, and the Political Economy of
AI Capability Measurement* (Esposito & Zhang, <https://arxiv.org/abs/2607.01254>) argues
that benchmark validity is bounded by the quality of expert human judgment embedded in its
construction. SpecTrap takes that seriously in the one way a weekend project can: **no
reported metric depends on a model's judgment.** Labels come from differential execution
against a hand-written reference and from assertions traceable to published standards;
scoring is an execution predicate. The language model in the referee assigns a triage
*category*, and no headline number is a function of that category.

## 3. What is *not* claimed

- **Not claimed:** that "generate tests without seeing the code" is novel. It is not — see
  Ma & Eisty and PGS above.
- **Not claimed:** that there is a published result showing the specific joint effect this
  project is named after (same model, same spec, implementation and tests written in mutual
  blindness, false-pass rate measured against an independent oracle). Every *link* in that
  chain is published; the joint measurement is not, which is why the forge measures it here
  instead of citing it. The number it produces is in [README.md](README.md#the-forge).
- **Not claimed:** statistical significance. SpecTrap has 10 held-out buggy cases. The
  power ceiling is stated before the result, in [CHANGELOG.md](CHANGELOG.md) and in
  `results/summary.json`.

## 4. Tools in the same space

| Tool | What it does | Relationship |
|---|---|---|
| [Hypothesis](https://hypothesis.readthedocs.io/) | property-based testing for Python | **Used** — the adversary emits Hypothesis properties, run derandomised |
| Meta TestGen-LLM / Qodo Cover / Diffblue Cover | raise coverage by generating tests that pass | Opposite objective: they add green tests, Blindspot looks for red ones |
| CodeRabbit / Greptile / Cursor Bugbot | LLM code review on diffs | Read the code and reason about it; no execution-verified soundness criterion, no spec-derived obligation ledger |
| `mutmut`, `cosmic-ray` | mutation testing | Complementary. Mutation score measures suite strength against synthetic mutants; Blindspot measures detection of a real defect a model actually wrote |
| CrossHair, `deal`, `icontract` | symbolic execution and contracts | Require the implementation (or annotations on it) as input — the dependency the barrier removes |
